# P1.3 Product Provenance — эксплуатационная инструкция

## Канонические команды

Перегенерация базы:

```bash
python3 tools/generate_product_provenance.py
```

Проверка отсутствия дрейфа:

```bash
python3 tools/generate_product_provenance.py --check
```

Аналитический второй проход:

```bash
python3 tools/analyze_product_provenance.py
```

P1.3-тест:

```bash
node tests/p1-3-product-provenance.test.js
```

Полный локальный gate:

```bash
python3 tools/release_gate.py --profile full
```

## Изменение карточки

1. Исправлять исходную карточку/метаданные или правила генератора, а не сгенерированный P1.3 chunk вручную.
2. Указывать конкретный source_id, dataset, версию, состояние и основание соответствия.
3. Не превращать неизвестное значение в `0` без явной zero policy.
4. После изменения запускать генератор, аналитику и P1.3-тест.
5. Изучать изменения статистики и review queue, а не принимать PASS только по синтаксису.

## Повышение confidence

HIGH разрешён только конкретной записи PRIMARY_DATASET. Название таблицы без record id недостаточно. Этикетка без стабильной идентификации не становится HIGH. Рецептурная модель и proxy не становятся HIGH даже при полной числовой заполненности.

## Работа с `ASSUMED_ZERO`

`ASSUMED_ZERO` сохраняет совместимость старого числового расчёта, но означает: «надёжное значение не установлено». Для замены требуются:

- явный ноль в первичном источнике → `SOURCE_REPORTED_ZERO`;
- конкретное измеренное значение → `MEASURED`;
- официальная этикетка → `LABEL`;
- документированная модель → `CALCULATED`/`IMPUTED`;
- отсутствие данных без числовой совместимости → `MISSING`.

## Дубли

Не удалять автоматически элементы из duplicate reports. Сначала проверить:

- различие сырого/готового состояния;
- бренд, рынок и упаковку;
- разновидность или сорт;
- единицы и базис 100 г/порция;
- реальный общий source_id;
- использование ключа в сохранённых рационах.

## Контроль modern/legacy

При изменении runtime quality logic необходимо проверять обе ветки. Provenance registry и quality engine должны быть идентичны; изменения calculation core, report builder и AI planner должны присутствовать в обеих активных ветках runtime manifest.
