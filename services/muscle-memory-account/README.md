# Muscle Memory account service

Серверный слой для аккаунтов и синхронизации прогресса анатомического тренажёра.

## Что хранится

- имя пользователя и email;
- хэш пароля — пароль в открытом виде не сохраняется;
- отдельная запись о согласии на обработку персональных данных;
- серверные сессии в защищённых HttpOnly/Secure/SameSite cookie и одноразовые токены восстановления доступа;
- состояние учебного прогресса: попытки, ошибки, интервальное повторение, пары путаниц и история занятий.

## Развёртывание

1. Создать PostgreSQL в российском дата-центре.
2. Создать Node.js-приложение из каталога `services/muscle-memory-account`.
3. Заполнить переменные окружения по `.env.example`.
4. Настроить SMTP для восстановления пароля и проверить фактическую схему передачи персональных данных.
5. Указать production-адрес тренажёра в `PUBLIC_APP_URL` и `APP_ORIGINS`.
6. В интерфейсе тренажёра оставить API same-origin либо указать его в meta `muscle-memory-api-base`.
7. Перенести runtime-ассеты тренажёра с внешних CDN/репозиториев в утверждённую production-инфраструктуру и только после проверки выставить `RUNTIME_ASSETS_LOCALIZED=true`.

Регистрация автоматически остаётся выключенной, пока не заполнены реквизиты оператора, версия согласия, SMTP, production URL, разрешённый origin и не подтверждена локализация runtime-ассетов.

## Юридический gate перед включением регистрации

Код не заменяет организационные обязанности оператора. Перед началом сбора персональных данных нужно:

- разместить первичную базу персональных данных граждан РФ на территории России;
- заполнить фактические реквизиты оператора в политике;
- проверить и утвердить отдельное согласие на обработку персональных данных;
- выполнить применимые требования статьи 22 Федерального закона № 152-ФЗ, включая уведомление Роскомнадзора до начала обработки, если нет законного исключения;
- проверить договоры и фактические маршруты данных у хостинга, PostgreSQL, резервного копирования и SMTP;
- перенести runtime-загрузку Three.js, Z-Anatomy, BodyParts3D и иных production-ассетов с внешних CDN/репозиториев на выбранную инфраструктуру до включения аккаунтов;
- не включать `CROSS_BORDER_TRANSFER=true` без отдельной юридической проверки соответствующего режима.

Политика и текст согласия формируются сервером из одной версии `PRIVACY_CONSENT_VERSION`. Это исключает ситуацию, когда форма регистрации ссылается на другую редакцию документа.

## Поведение клиента

Cloudflare Pages-preview не включает регистрацию и продолжает хранить прогресс локально. На российском production-сервере клиент получает `/api/account/config`, показывает регистрацию только после прохождения legal gate и синхронизирует существующий локальный прогресс после входа.

При конфликте версий клиент объединяет локальный и серверный учебный store и повторяет сохранение, поэтому вход с другого устройства не должен стирать уже накопленную историю.

## Проверка перед merge

Feature-ветка должна пройти быстрые проверки тренажёра, интеграционный тест аккаунтов с PostgreSQL и полный браузерный smoke до переноса в релизную ветку.

Отдельное согласие в интерфейсе вынесено в самостоятельный шаг после заполнения данных аккаунта.

На узких экранах вход в аккаунт расположен ниже основной анатомической рабочей области, чтобы не уменьшать высоту 3D-модели.

Финальная проверка: полный браузерный smoke запускается на актуальном HEAD feature-ветки перед слиянием.

Браузер не хранит bearer-токен сессии в `localStorage`; production-сессия поддерживается защищённой cookie.
