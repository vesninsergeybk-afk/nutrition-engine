# Nutrient — обновления каталога для автономного Android-приложения

Данный каталог — **подготовленный интерфейс обновления данных**, а не уже встроенный в APK механизм. Сайт использует те же проверенные дополнительные записи, но Android-клиенту ещё предстоит реализовать чтение этого формата. До появления клиента нельзя считать, что уже установленные APK обновляются.

## Файлы

- `manifest.json` — небольшое актуальное описание с `current_revision`, `base_dataset`, `base_count`, `expected_merged_count`, `overlay_path`, `overlay_sha256` и `overlay_bytes`.
- `revisions/2026-10-24.1.json` — неизменяемый полный снимок **всех одобренных дополнений** относительно базовой базы из 1105 продуктов: шесть добавлений, одна защищённая коррекция.
- `tools/build_catalog_update_feed.cjs` — воспроизводимо собирает оба файла из подключённых к сайту источников. После расширения каталога нужно создавать **новую ревизию и новый файл**, не перезаписывая старые ревизии. Версия `current_revision` в манифесте должна увеличиваться.

## Как APK должен обновлять базу

1. В установочный APK входит исходная база `products.v5.3.210-p1.3` (1105 продуктов) и проверенная версия дополнений. Запуск и весь основной расчёт работают без интернета.
2. При наличии сети клиент выполняет небольшой запрос `GET /updates/catalog/v1/manifest.json` с запретом использовать устаревший кэш (либо берёт файл из `https://raw.githubusercontent.com/vesninsergeybk-afk/nutrition-engine/main/updates/catalog/v1/manifest.json`).
3. Если `current_revision` новее локальной и `base_dataset` точно совпадает, клиент загружает `overlay_path`, разрешённый **только внутри каталога `updates/catalog/v1/revisions/`** того же доверенного источника. Никаких произвольных URL из манифеста.
4. До установки проверяет размер байтов, SHA-256, схему `nutrient-catalog-overlay/v1`, идентификатор базы, уникальность ключей, отсутствие пересечения с каноническими ключами, все 33 числовых показателя и число продуктов после объединения.
5. Для `corrections` клиент сначала проверяет идентификатор и описание записи USDA из неизменяемой базы. Если исходная запись уже изменилась, **не применяет** коррекцию вслепую.
6. Клиент сохраняет снимок и номер ревизии **одной транзакцией** во временное хранилище и переключается на новый только после проверки. При любой ошибке, прерывании скачивания или отсутствии интернета остаётся старая исправная база.
7. Пользовательские рационы и записи должны ссылаться на постоянный `key` продукта; обновление не удаляет пользовательские данные.

Снимок **полный относительно указанной базовой версии**, а не цепочка последовательных патчей: клиенту достаточно самого нового снимка, если его базовая версия совпадает.

## Публикация и кэш

- Манифест должен отдаваться с `Cache-Control: no-cache, no-store, must-revalidate`; путь ревизии может кэшироваться неизменно.
- Файлы в `main` публичны **только после слияния PR и успешного развёртывания**. Ссылка на ветку PR не является стабильным адресом обновлений.
- Цифры для пяти универсальных продуктов взяты из USDA SR Legacy, а микроэлементы творога 2% смоделированы отдельно. Файл не утверждает, что все 33 показателя измерены у товаров конкретного магазина.
- HTTPS и SHA-256 позволяют обнаружить случайную порчу данных. Если потребуется защищаться от компрометации самого репозитория, нужно дополнительно подписывать манифест независимым ключом и проверять подпись в APK.

Контрольная сборка: `node tools/build_catalog_update_feed.cjs`. Чтобы убедиться, что опубликованная ревизия соответствует источникам: `node tests/catalog-update-contract.test.cjs`.
