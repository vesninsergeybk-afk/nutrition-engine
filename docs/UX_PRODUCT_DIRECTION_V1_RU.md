# Направление UX/UI калькулятора — v1

Дата фиксации: 2026-09-26  
Статус: рабочий источник истины для следующего цикла интерфейса.  
Расчётное ядро, нормативы и научная логика не меняются этим документом.

## 1. Продуктовая концепция

Калькулятор должен оставаться глубоким профессиональным инструментом, но не требовать от пользователя постоянно держать в памяти предыдущие экраны.

Базовая модель:

**единое состояние приложения → свободно переключаемые рабочие вкладки → постоянная прогрессивная сводка («спутник пользователя») → необязательное представление «Лента / Все данные».**

Главные рабочие области:
1. Потребности
2. Рацион
3. Анализ
4. Улучшить
5. Отчёт

Это не мастер «шаг 1 → шаг 2 → шаг 3». Пользователь может в любой момент вернуться в любой раздел без потери уже введённых данных.

Режим «Лента / Все данные» не является отдельной логикой приложения. Он показывает то же состояние в непрерывном представлении и синхронизируется с вкладками.

## 2. Неприкосновенные принципы

- Не удалять полезные возможности ради чистоты экрана.
- Не дублировать расчётную логику в UI.
- Не создавать второе независимое состояние для спутника.
- Переход по вкладкам не должен сбрасывать рацион, профиль, фильтры, выбранные представления и по возможности позицию прокрутки.
- Кнопка Back/Forward браузера должна возвращать к предыдущему рабочему контексту.
- Подробные объяснения сохраняются, но не конкурируют визуально с результатом и следующим действием.
- Полный список микро- и макронутриентов остаётся одной из ключевых ценностей продукта.
- HEI, Гарвардская тарелка, матрица качества/структуры, рекомендации и отчёт остаются доступны.
- Любое изменение presentation layer проходит реальные пользовательские сценарии и браузерный контроль.

## 3. Спутник пользователя

### 3.1. Назначение

Спутник — не второй отчёт и не отдельный Dashboard.

Он всегда отвечает максимум на четыре вопроса:

1. Для кого считаем?
2. Какие ориентиры?
3. Что получилось в текущем рационе?
4. Что сейчас требует внимания?

Каждый показатель является кратким входом в подробный раздел.

### 3.2. Прогрессивное заполнение

#### Состояние A — потребности ещё не рассчитаны
Показывать:
- короткий статус;
- одно действие «Рассчитать потребности».

#### Состояние B — потребности рассчитаны
Показывать:
- компактный профиль;
- энергия;
- белки / жиры / углеводы;
- при необходимости один дополнительный ориентир, если он критичен для активного сценария.

#### Состояние C — рацион заполнен
Добавить:
- фактическую энергию / ориентир;
- Б / Ж / У: факт против ориентира;
- число продуктов или приёмов пищи только если это помогает понять состояние.

#### Состояние D — доступны нутриентные данные
Добавить:
- сколько показателей в пределах ориентира;
- сколько требуют внимания;
- сколько имеют неполные данные;
- мини-визуализацию только как overview, без полного списка.

#### Состояние E — доступны качество и структура
Добавить:
- HEI;
- структура;
- до трёх главных приоритетов.

### 3.3. Жёсткий бюджет информации

В свернутой/базовой форме спутник не должен показывать:
- полный список нутриентов;
- методику расчёта;
- подробные рекомендации;
- большие диаграммы;
- длинный текст;
- больше трёх приоритетов одновременно.

### 3.4. Desktop

Предпочтительная гипотеза для прототипа:
- правая sticky-колонка 288–320 px;
- рабочая область слева minmax(0, 1fr);
- спутник остаётся на экране при переходе между вкладками;
- на небольшом desktop/tablet колонка превращается в горизонтальную компактную панель.

### 3.5. Mobile

- одна компактная строка высотой около 48–56 px;
- пример: «1630 / 2275 ккал · 5 требуют внимания»;
- раскрытие по нажатию;
- подробная версия — bottom sheet / disclosure, не постоянный высокий блок;
- закрытие возвращает пользователя в ту же позицию;
- нижняя навигация не перекрывается.

### 3.6. Техническая модель

Спутник читает уже существующее каноническое состояние и события приложения.

Он не должен:
- пересчитывать нормы;
- иметь свою копию рациона;
- хранить независимые HEI/микронутриентные значения.

Первый implementation pass — только read-only слой + переходы в существующие разделы.

## 4. Анализ

Внутренний второй уровень анализа рекомендуется прототипировать как:

**Сводка · Нутриенты · Качество · Структура**

- Сводка: несколько главных выводов.
- Нутриенты: полный микро-/макронутриентный анализ, фильтры и вклад продуктов.
- Качество: HEI-2020 и компоненты.
- Структура: Гарвардская тарелка + компактная матрица качества/структуры.

Название «HEI-2020» сохраняется в содержании, но главный пользовательский ярлык может быть «Качество».

Большая диагностическая матрица не должна быть hero-блоком по умолчанию. В базовом виде: HEI, структура, краткая интерпретация и мини-матрица; полный график — по раскрытию.

## 5. Дизайн-система v1

Цель: современный профессиональный научно-клинический интерфейс, а не маркетинговая страница и не административная панель.

### 5.1. Типографика

Главная проблема текущего интерфейса не только в гарнитуре, а в неравномерной иерархии: слишком много жирного текста, мелких подписей и одинаково сильных заголовков.

Для прототипа:
- базовый текст desktop: 15 px / 22 px;
- базовый текст mobile: 16 px / 24 px;
- auxiliary: 12–13 px / 16–18 px;
- H1 рабочего экрана: 26–28 px / 32–36 px, 650–700;
- H2: 20–22 px / 26–30 px, 650–700;
- H3: 16–18 px / 22–24 px, 600–650;
- button: 14–15 px / 20 px, 600;
- значения KPI могут быть крупнее текста, но без 800–900 веса по умолчанию.

Не использовать ALL CAPS как обычный способ создать иерархию.

Гарнитура:
- сначала прототипировать на хорошем native/system stack;
- отдельно сравнить с Inter Variable (при локальном подключении) на русском тексте и плотных числовых таблицах;
- менять шрифт только после A/B визуального сравнения, а не как косметический жест.

### 5.2. Кнопки

Четыре уровня:
- Primary — одно главное действие в текущем контексте;
- Secondary — важное, но не главное;
- Ghost/Tertiary — навигация, раскрытие, служебные действия;
- Destructive — удаление.

Размеры:
- desktop productive: 40 px;
- mobile / частые touch actions: не менее 44 px;
- горизонтальный padding обычно 14–16 px;
- radius 8–10 px;
- не растягивать кнопку по высоте карточки;
- full-width на мобильном только когда это действительно основное действие.

Primary:
- насыщенный фирменный синий;
- белый текст;
- без декоративного градиента;
- минимальная или отсутствующая тень.

Secondary:
- белая/нейтральная поверхность;
- спокойная граница;
- тёмный текст.

Ghost:
- без постоянной рамки;
- фон появляется по hover/focus.

Delete:
- красный текст/outline в списках;
- насыщенно-красная заливка только в подтверждении разрушительного действия.

### 5.3. Поверхности

- фон приложения: один нейтральный слой;
- рабочая поверхность: белая;
- вспомогательная поверхность: очень светлая нейтральная;
- не более 2–3 визуальных уровней одновременно;
- radius: 10–12 px для крупных поверхностей, 8–10 px для контролов;
- pills использовать только для тегов/статусов, а не для каждого параметра;
- тени редкие и слабые; иерархию в основном задают пространство, линия и типографика.

### 5.4. Пространство и пропорции

Базовая шкала: 4 / 8 / 12 / 16 / 24 / 32 px.

Рабочий контент:
- desktop: ограничивать строку чтения и не растягивать смысловой текст на всю ширину;
- при спутнике рабочая колонка ориентировочно 720–860 px, спутник 288–320 px;
- между крупными разделами 24–32 px;
- внутри блока 12–16 px;
- внутри плотных строк данных 8–12 px.

### 5.5. Таблицы и нутриентные списки

- данные должны выглядеть как данные, а не как сетка отдельных карточек;
- строки 40–48 px для однострочных значений;
- заголовок столбца 13–14 px / 600;
- строка 14–15 px / 400–500;
- числовые значения выравнивать последовательно;
- полный нутриентный список поддерживает фильтры и раскрытие вкладчиков;
- статус сообщается не только цветом.

### 5.6. Цвет

Фирменный синий сохраняется, но используется существенно реже.

Роли цвета:
- primary — действие/активная навигация;
- green — подтверждённое благополучное состояние;
- amber — внимание;
- red — проблема/разрушительное действие;
- neutral — всё остальное.

Нельзя использовать синий одновременно как кнопку, рамку, фон карточки, чип, статус и декоративный акцент на одном экране.

## 6. Первые сценарии приёмки

Новый shell/спутник считается полезным только если начинающий пользователь может без чтения инструкции:

1. рассчитать потребности;
2. вернуться к ним после перехода в рацион;
3. добавить продукт и изменить граммовку;
4. увидеть в спутнике факт против ориентира;
5. открыть полный список витаминов и минералов;
6. увидеть вклад продуктов в выбранный нутриент;
7. открыть HEI/качество;
8. открыть структуру/тарелку;
9. применить одну рекомендацию;
10. получить отчёт;
11. переключиться «Вкладки ↔ Лента» без потери состояния.

## 7. План реализации

### Pass 0 — прототип и измерения
- сделать спутник read-only за feature flag;
- desktop + mobile;
- не менять маршруты и расчёты;
- проверить заполненное и пустое состояния.

### Pass 1 — навигационная обратимость
- вкладки доступны всегда;
- профиль/потребности возвращаются одним действием;
- Back/Forward;
- сохранение scroll и локального состояния.

### Pass 2 — современная базовая дизайн-система
- токены типографики;
- единая шкала кнопок;
- нормализация радиусов, полей, таблиц и spacing;
- устранение растянутых синих кнопок и пустых карточек.

### Pass 3 — спутник v1
- needs → ration → nutrients → quality;
- кликабельные переходы;
- mobile disclosure / desktop sticky;
- бюджет информации и progressive disclosure.

### Pass 4 — Анализ
- Сводка / Нутриенты / Качество / Структура;
- явный доступ к Гарвардской тарелке;
- компактная матрица + полный вид по запросу.

### Pass 5 — Лента / Все данные
- синхронизация с текущей вкладкой;
- локальная навигация по разделам;
- сохранение текущего контекста.

### Pass 6 — пользовательский destructive audit
Сравнить старый и новый интерфейс на одинаковых задачах по:
- числу действий;
- потерям контекста;
- вынужденному чтению;
- прокрутке;
- ошибочным переходам;
- времени до первого результата.

## 8. Что не делать

- Не начинать с тотального переписывания DOM.
- Не удалять полотно до проверки нового shell.
- Не делать Dashboard отдельным большим экраном.
- Не превращать спутник в длинный отчёт.
- Не менять шрифт и цвета изолированно от иерархии.
- Не вводить новые клинические режимы навигации до готовности соответствующих расчётных контрактов.
- Не считать зелёный CI доказательством хорошего UX.
