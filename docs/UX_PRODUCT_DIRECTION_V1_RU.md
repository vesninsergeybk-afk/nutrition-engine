# UX Release 0 — контракт интерфейса калькулятора

Дата фиксации: 2026-09-26  
Статус: контрольная точка архитектуры перед первым кодовым UX-релизом.  
Базовая версия приложения: main @ 35ab292379e1f10eaa468f83a51b819852bd6900.  
Область изменений Release 0: только документация. Расчётное ядро, нормативы, продуктовая база, runtime, формулы и клинические ограничения этим релизом не меняются.

Этот документ заменяет прежнюю рабочую модель UX/UI в этой ветке и становится источником истины для следующих интерфейсных релизов. Он фиксирует не конкретный макет, а требования, которые должны пережить смену компоновки.

---

## 1. Цель Release 0

Калькулятор должен оставаться глубоким профессиональным инструментом. Упрощать нужно путь пользователя через сложность, а не саму аналитическую модель.

Новая архитектура считается удачной, только если одновременно выполняются два условия:

1. пользователь быстрее понимает, где он находится, что произошло и что можно сделать дальше;
2. существующие полезные возможности не исчезают и не становятся существенно труднее только ради визуальной чистоты.

Release 0 не утверждает окончательный внешний вид. Он фиксирует:

- UX-gate;
- пять рабочих задач верхнего уровня;
- карту сохраняемых возможностей;
- модель состояния и зависимостей;
- правила навигации, Back/Forward и семантического возврата;
- информационную архитектуру анализа;
- правила раскрытия сложных и профессиональных функций;
- контракт desktop/tablet/mobile;
- разрушительные acceptance-сценарии;
- границы будущих релизов.

---

## 2. Что уже решено, а что остаётся гипотезой

### 2.1. Решения высокой уверенности

- У приложения должен быть один канонический источник данных профиля и рациона.
- Производные расчёты не становятся самостоятельным источником истины.
- Пользователь должен свободно переходить между задачами без повторного ввода и неожиданного сброса.
- Результат не должен выглядеть актуальным, если изменились данные, от которых он зависит.
- Анализ и редактирование рациона должны образовывать короткий повторяемый цикл.
- Полный микро- и макронутриентный анализ остаётся ключевой возможностью.
- HEI, структурный анализ, строгая Гарвардская тарелка, качество исходных данных и профессиональный отчёт сохраняются.
- Клинические и защищённые сценарии не могут быть спрятаны так, чтобы пользователь обошёл ограничения.
- AI не является расчётным ядром: числовой эффект проверяет детерминированная логика приложения.
- Dashboard является первым уровнем раздела «Анализ», а не отдельной шестой домашней страницей.
- Mobile может иметь другую композицию, но не другую модель данных и не урезанный набор основных задач.
- Зелёный CI не считается доказательством хорошего UX: обязательна проверка реального пользовательского поведения.

### 2.2. Гипотезы, которые Release 0 намеренно не закрепляет

- постоянный «спутник» пользователя;
- правая sticky-колонка;
- горизонтальная строка контекста;
- mobile bottom sheet;
- представление «Все данные» или длинное полотно;
- конкретное число внутренних вкладок анализа;
- точная форма аналитического dashboard;
- сохранение нынешней большой матрицы качества и структуры;
- конкретная гарнитура, радиусы, тени и размеры компонентов;
- одинаковая физическая форма навигации на desktop и mobile.

Любая из этих гипотез может быть принята, изменена или отвергнута без пересмотра Release 0, если она не нарушает зафиксированные ниже требования.

## 3. UX-gate

Каждый следующий интерфейсный релиз проверяется по этим инвариантам. Здесь нет суммарного балла: критическую потерю нельзя компенсировать красивой визуализацией.

### G1. Единое состояние данных
Профиль, применённые потребности и рацион имеют один канонический источник. Представления не создают независимые копии.

### G2. Нет незаметно устаревших результатов
После изменения входных данных зависимые результаты либо пересчитываются, либо явно переходят в состояние ожидания, устаревания или необходимости пересчёта.

### G3. Навигация обратима
Пользователь может покинуть текущую задачу и вернуться без повторного ввода и неожиданного сброса.

### G4. Текущее положение понятно
После перехода понятно, какая задача и какой локальный контекст открыты.

### G5. Основные возможности обнаружимы
Потребности, рацион, полный анализ нутриентов, HEI, структура, коррекция и отчёт нельзя потерять из-за редизайна.

### G6. От вывода можно дойти до основания
Из сводного отклонения можно открыть подробные данные, вкладчики и применимый ориентир, а затем вернуться обратно.

### G7. Редактирование связано с результатом
После изменения рациона пользователь понимает, какие результаты обновились, и может быстро проверить эффект.

### G8. Состояния данных различаются семантически
Настоящий ноль, отсутствие данных, неполные данные, ещё не рассчитанное значение, загрузка, устаревший результат и ошибка не выглядят одинаково.

### G9. Основные задачи сохраняются на разных экранах
Desktop и mobile могут иметь разную компоновку, но не разные продуктовые возможности.

### G10. Альтернативные представления синхронны
Если появятся несколько способов просмотра одних данных, они используют одно состояние и не расходятся.

### G11. Интерфейс не заставляет держать важные числа в памяти
Данные, необходимые для текущего решения, показываются рядом или естественно вызываются.

### G12. Каждая постоянная интерфейсная сущность решает самостоятельную задачу
Панель, карточка, вкладка или «спутник» не должны существовать только потому, что для них нашлось место.

### G13. Актуальность результата видима
Пользователь должен понимать случаи «профиль изменён, но ещё не применён», «коррекция построена для предыдущего рациона», «черновик распределения устарел», «расчёт основан на неполных продуктовых данных».

### G14. Сохраняемая возможность не исчезает молча
Если старый способ реализации меняется, та же пользовательская задача должна оставаться выполнимой не хуже либо её удаление должно быть отдельным осознанным продуктовым решением.

## 4. Архитектура верхнего уровня

На уровне задач приложение состоит из пяти рабочих областей:

1. Потребности
2. Рацион
3. Анализ
4. Улучшить
5. Отчёт

Это информационная архитектура, а не обязательное требование «пять одинаковых вкладок».

### 4.1. Потребности
Задача: определить и применить профиль, нормативный контекст и персональные ориентиры.

Не должна превращаться в обязательный мастер, который блокирует возврат к другим данным.

### 4.2. Рацион
Задача: собрать и редактировать фактический или планируемый набор продуктов и количества.

Это основная рабочая поверхность для изменений состава рациона.

### 4.3. Анализ
Задача: понять, что получилось, где есть отклонения, насколько надёжны данные и почему сформировался результат.

Нутриенты, HEI, структура, Гарвардская тарелка и качество данных являются слоями одной аналитической среды, а не независимыми приложениями.

### 4.4. Улучшить
Задача: подготовить проверяемое изменение рациона, оценить его последствия и применить только после подтверждения пользователя.

Предложение остаётся черновиком до явного применения.

### 4.5. Отчёт
Задача: собрать текущий расчётный снимок в плотную профессиональную выдачу для просмотра, печати, PDF и передачи.

Отчёт не хранит вторую версию расчёта.

## 6. Каноническая модель состояния

Имена ниже концептуальны и не навязывают конкретный API.

| Слой | Содержание | Правило |
|---|---|---|
| Profile Draft | текущие значения формы профиля | может отличаться от применённого профиля |
| Applied Profile / Needs | последний успешно рассчитанный профиль и потребности | используется зависимыми расчётами |
| Norm Policy | DRI/EFSA, пользовательские нормы и применимые правила | отдельная зависимость нормативного анализа |
| Ration | продукты, количества, составные блюда | один канонический рацион |
| Derived Analysis | КБЖУ, нутриенты, HEI, структура, Harvard, качество данных | воспроизводится из входов, не является владельцем данных |
| Improvement Draft | ещё не применённый набор изменений | не меняет рацион до подтверждения |
| Meal Draft | распределение текущего рациона по приёмам | может стать устаревшим |
| UI Context | активная задача, показатель, фильтр, раскрытая детализация | не содержит копии расчётных значений |
| Persistence | то, что восстанавливается после reload | не создаёт второе независимое состояние |

Для реализации допускаются внутренние ревизии, например revision применённого профиля, рациона и нормативной политики. Названия и способ хранения выбираются в кодовом релизе. Смысл один: производный результат должен знать, из каких входов он получен.

## 7. Матрица зависимостей

| Изменение | Что должно обновиться или стать неактуальным | Что не должно сбрасываться |
|---|---|---|
| Изменение Profile Draft без применения | только статус «есть неприменённые изменения» | Applied Profile, рацион и текущие расчёты |
| Применение нового профиля | потребности и все производные выводы/черновики, которые используют эти потребности; Improvement Draft требует повторной проверки, если его цели зависят от профиля | сам рацион и его абсолютный состав |
| Изменение возраста/пола/массы/активности после применения | персональные ориентиры и сравнение с ними; зависимые приоритеты анализа и коррекции | фактические нутриенты рациона; HEI, если его входы не зависят от этих параметров |
| DRI ↔ EFSA | нормативное сравнение соответствующих микронутриентов; зависимые приоритеты и Improvement Draft требуют повторной проверки | продукты, абсолютный состав, HEI |
| Пользовательская норма | показатели и предложения коррекции, которые используют изменённый ориентир | остальные независимые результаты |
| Добавление/удаление продукта | все результаты, зависящие от рациона | применённый профиль |
| Изменение количества продукта | все результаты, зависящие от рациона | применённый профиль |
| Изменение рациона после построения Improvement Draft | черновик коррекции требует повторной проверки | сам новый рацион |
| Изменение рациона после построения Meal Draft | черновик приёмов помечается устаревшим либо обновляется только по явно выбранному режиму | сам новый рацион |

Запрещён упрощённый глобальный подход «изменилось что-нибудь → всё устарело», если зависимость можно определить точнее. Он делает интерфейс менее достоверным и менее полезным.

---

## 8. Навигация и семантический возврат

### 8.1. Базовое правило
История должна сохранять смысл места, а не только координату прокрутки.

Пример контекста:

Анализ → Нутриенты → Железо → Основные вкладчики.

Пользователь переходит в рацион, меняет продукт и возвращается. Интерфейс должен открыть тот же смысловой контекст уже с пересчитанными данными.

### 8.2. Что относится к значимому переходу
В историю браузера попадают переходы, которые пользователь воспринимает как смену рабочего места: другая задача, отдельный аналитический объект или другой существенный контекст.

Обычное раскрытие справки, аккордеона или локального пояснения не обязано создавать отдельный шаг Back.

### 8.3. Back / Forward
Back и Forward восстанавливают:

- рабочую область;
- смысловой объект, если он был выбран;
- применимые локальные фильтры;
- раскрытие, если оно необходимо для продолжения задачи;
- позицию как дополнительное удобство, но не как единственный способ восстановления.

### 8.4. Reload
После перезагрузки:

- сохранённые профиль и рацион восстанавливаются по своим правилам;
- применённый профиль не подменяется незавершённым черновиком;
- маршрут восстанавливается только если его предпосылки доступны;
- если deep link требует ещё не существующих данных, показывается понятное состояние с действием для продолжения, а не пустой или сломанный экран.

### 8.5. Семантический контекст не хранит значения
Контекст может помнить «железо / вкладчики», но не собственную копию числа железа, процента нормы или списка продуктов. После возврата значения снова читаются из актуального расчёта.

## 9. Информационная архитектура анализа

Раздел «Анализ» строится слоями.

### Уровень 1. Сводка
Цель: быстро понять общее состояние и несколько действительно важных отклонений.

Сводка не обязана показывать проблему, если подтверждённой проблемы нет.

### Уровень 2. Области анализа
Доступны как минимум:

- нутриенты и нормы;
- HEI/качество;
- структура;
- качество и полнота исходных данных.

Физическая реализация может быть локальной навигацией, сегментами, якорями или другим способом. Release 0 не требует ровно четырёх под-вкладок.

### Уровень 3. Конкретный показатель
Для нутриента или компонента пользователь видит:

- факт;
- применимый ориентир;
- статус;
- полноту данных;
- при необходимости границу безопасности;
- переход к источникам вклада.

### Уровень 4. Основание вывода
Вкладчики, методические сведения, ограничения и качество исходных карточек раскрываются по запросу.

### Запреты
- Не создавать искусственный общий score для группы нутриентов без научного основания.
- Не трактовать неполные данные как доказанный недостаток.
- Не выдавать верхний допустимый уровень за целевое значение.
- Не дублировать один и тот же вывод несколькими большими карточками.
- Не делать большую диагностическую матрицу обязательным hero-блоком только потому, что она визуально эффектна.

---

## 10. Progressive disclosure без функционального обеднения

Сложность распределяется по смыслу задачи.

### Потребности
- основные обязательные поля;
- цели и предпочтения;
- специальные/профессиональные параметры;
- защищённые поля автоматически становятся видимыми при выборе соответствующего сценария.

### Рацион
- поиск и рабочий список;
- альтернативные способы ввода;
- каталог, JSON, пресеты и распределение по приёмам как связанные инструменты рациона.

### Анализ
- сводка;
- полный анализ;
- вкладчики и методика по запросу.

### Улучшить
- конкретное действие;
- проверяемые последствия;
- ограничения;
- подробное объяснение по запросу;
- AI как дополнительный слой, а не обязательный путь.

### Отчёт
- плотная профессиональная выдача;
- настройка состава;
- экспорт.

Не создавать один общий склад «Дополнительно», в котором смешаны безопасность, методика, импорт, каталог и служебные функции.

---

## 11. Responsive contract

Числа 390, 820 и 1440 px являются обязательными тестовыми точками, а не заранее заданными CSS-breakpoint.

### 11.1. 1440 px
- допускается несколько колонок, если рабочая область не становится тесной;
- ориентир порядка 1200 px для основной композиции остаётся разумной стартовой точкой, но не жёстким токеном;
- постоянная боковая панель допускается только если она реально помогает и не ухудшает таблицы, редактор и читаемость;
- длинный текст не растягивается на всю доступную ширину.

### 11.2. 820 px
Это отдельный критический gate.

Проверяются:
- отсутствие двух слишком узких рабочих колонок;
- отсутствие «desktop, только уменьшенного»;
- доступность навигации и фильтров;
- отсутствие необходимости уменьшать основной текст ради сохранения компоновки;
- удобство длинных таблиц и форм.

### 11.3. 390 px
- одна основная рабочая колонка;
- текущая задача должна доминировать над служебным UI;
- полный анализ сохраняется, но раскрывается последовательно;
- клавиатура поиска не перекрывает критические действия;
- таблица не переносится на телефон простым уменьшением шрифта;
- важные действия имеют пригодную для касания область.

### 11.4. Дополнительные обязательные условия
- 125–150% zoom на desktop;
- длинные русские и коммерческие названия;
- составные блюда;
- большие значения и единицы;
- ошибки и длинные сообщения состояния;
- отсутствие горизонтального overflow там, где он не является осознанным способом просмотра вторичных столбцов.

## 12. Destructive acceptance matrix

### C1. Состояние и переходы

Обязательные сценарии:

1. первый расчёт: профиль → потребности → рацион → анализ;
2. анализ конкретного нутриента → рацион → изменение → возврат к тому же нутриенту;
3. несколько последовательных циклов «увидел → изменил → проверил»;
4. изменение Profile Draft без применения;
5. применение нового профиля при уже заполненном рационе;
6. DRI ↔ EFSA при открытом анализе;
7. Back / Forward между значимыми контекстами;
8. reload;
9. deep link в анализ;
10. защищённый сценарий и попытка запустить недопустимую автоматизацию.

Pass: пользователь не теряет данные, не получает ложную актуальность и не обязан заново искать смысловое место.

### C2. Экстремальное содержание

Обязательные сценарии:

- пустой рацион;
- один продукт;
- 20–40 продуктов;
- длинные названия;
- несколько комплексных блюд;
- очень много одновременных отклонений;
- рацион без значимых подтверждённых отклонений;
- частичные данные по части нутриентов;
- показатель без данных;
- AI недоступен.

Pass: интерфейс сохраняет иерархию, не создаёт ложных нулей, не превращает каждый показатель в огромную карточку и не скрывает полный массив данных.

### C3. Экран и композиция

Обязательные точки:

- 390 px;
- 820 px;
- 1440 px;
- 125–150% zoom;
- mobile с открытой клавиатурой.

Pass: основные задачи остаются выполнимыми, нет критических перекрытий, мелкого рабочего текста и вынужденного горизонтального скролла основной композиции.

### C4. Capability preservation

Перед границей каждого релиза таблица CAP проверяется по принципу:

- возможность осталась;
- возможность стала доступнее;
- либо способ изменён, но задача выполняется не хуже.

Любая непреднамеренная потеря safety/core-возможности блокирует релиз.

---

## 13. Что означает dashboard в будущей версии

Dashboard — первый уровень «Анализа».

Он должен помогать:

- понять общий статус;
- заметить несколько важных отклонений;
- перейти к основанию вывода;
- перейти к корректирующему действию.

Он не должен:

- заменять полный анализ;
- повторять весь отчёт;
- превращать десятки нутриентов в десятки декоративных графиков;
- создавать отдельное состояние;
- становиться обязательной домашней страницей приложения.

Размер графика должен соответствовать объёму информации, которую он действительно несёт.

---

## 14. Статус «спутника» и «Все данные»

### Спутник
Статус: гипотеза.

Он может оказаться:
- компактной строкой контекста;
- адаптивной боковой панелью на широком экране;
- раскрываемой сводкой;
- либо вообще не понадобиться, если семантический возврат и локальный контекст решат задачу лучше.

Если он реализуется, первая версия только читает каноническое состояние. Никаких собственных расчётов и копий данных.

### «Все данные» / полотно
Статус: гипотеза.

Такое представление допускается только как проекция того же состояния. Оно не должно:
- иметь отдельный рацион;
- иметь отдельные фильтры без синхронизации;
- становиться обязательным способом добраться до скрытых функций.

Если вкладочная/задачная архитектура уже обеспечивает хороший доступ ко всем данным, отдельное полотно может не понадобиться.

---

## 15. Организация следующих релизов

### Release 1 — навигационная обратимость
Цель: исправить фундамент переходов без большого визуального редизайна.

Объём:
- устойчивый доступ к пяти задачам;
- semantic return;
- Back/Forward;
- reload/deep-link semantics;
- сохранение осмысленного локального контекста;
- отсутствие сброса данных.

Не входит:
- перестройка всех карточек;
- новый dashboard;
- спутник;
- изменение расчётного ядра.

### Release 2 — UI foundation
- типографическая шкала;
- роли кнопок;
- поля;
- строки данных;
- поверхности;
- spacing;
- радиусы;
- цветовые роли;
- удаление очевидных визуальных дефектов через единые примитивы, а не новый слой hotfix.

### Release 3 — контекстная поддержка
Не «спутник любой ценой».

Сначала измеряется, какие проблемы контекста остались после Release 1. Только затем выбирается минимальное средство: строка, локальная сводка, адаптивная панель или иной вариант.

### Release 4 — аналитический dashboard
- общий статус;
- ключевые отклонения;
- ясная обнаруживаемость полного анализа;
- HEI;
- структура;
- Гарвардская тарелка;
- качество данных;
- переходы к подробностям и коррекции.

Референс dashboard Бордакова используется как визуальный ориентир плотности и читаемости, но не как источник продуктовой архитектуры.

### Release 5 — «Все данные» при доказанной необходимости
Реализуется только если после Release 4 остаётся пользовательская задача, которую task-oriented интерфейс решает хуже непрерывного представления.

### Release 6 — коррекция и отчёт
- «действие сначала, объяснение по запросу» в коррекции;
- плотный профессиональный отчёт;
- сохранение глубины и источников данных.

### Release 7 — финальный destructive audit
Ручные и браузерные сценарии на нескольких размерах и в разных состояниях данных.

## 16. Release discipline

- Один мыслительный проход — одна задача.
- Один кодовый релиз — одна группа связанных изменений.
- После небольших изменений используется быстрый gate.
- Полный Chromium/Firefox/WebKit/WCAG запускается на границе релиза, а не после каждой косметической правки.
- CI проверяет регрессии, но не заменяет пользовательский аудит.
- Не добавлять hotfix-слой, если проблему можно решить в общем компоненте или контракте состояния.
- Архитектурный инвариант меняется только отдельным решением с обновлением этого документа.
- Гипотеза компоновки может меняться свободно, если UX-gate и capability contract сохраняются.

---

## 17. Stop conditions

Работу над конкретным релизом нужно остановить и пересмотреть решение, если для его реализации требуется хотя бы одно из следующего:

- второе независимое состояние профиля или рациона;
- собственный расчёт в dashboard/спутнике;
- скрытая потеря core/safety-возможности;
- старый результат, который выглядит новым;
- специальное исключение навигации для каждого отдельного нутриента;
- дублирование одного содержания в нескольких больших панелях без новой задачи;
- уменьшение основного текста только ради сохранения desktop-композиции на узком экране;
- обязательная зависимость базового калькулятора от AI;
- превращение «Дополнительно» в склад несвязанных функций;
- заметное ухудшение короткого цикла «анализ → изменение → проверка».

---

## 18. Готовность к Release 1

Release 1 можно начинать, если выполнено всё:

- этот документ принят как источник истины;
- PR Release 0 меняет только документацию;
- capability contract зафиксирован;
- state/dependency contract зафиксирован;
- semantic return определён;
- C1–C4 зафиксированы как acceptance-gates;
- спутник, «Все данные» и точная форма dashboard не считаются обязательными;
- разработчик может изменить навигацию, не принимая по ходу работы новых архитектурных решений.

---

## 19. Базовые артефакты текущей реализации

Release 0 опирается на уже существующие и проверенные части приложения, но не объявляет их текущую форму вечной:

- navigation shell и история маршрутов;
- persistence профиля с различением черновика и применённого состояния;
- восстановление рациона;
- detailed nutrient/HEI workspace;
- analysis feature continuity;
- единый report model;
- interaction-state contract;
- acceptance-тесты навигации, профиля, аналитики, responsive и доступности.

Их задача в следующих релизах — служить защитой от регрессий и источником проверенных паттернов, а не диктовать новый внешний вид.

---

## 20. Definition of Done Release 0

Release 0 завершён, когда:

1. один канонический UX-контракт находится в репозитории;
2. он отделяет инварианты от гипотез;
3. защищает функциональную глубину калькулятора;
4. описывает модель состояния и зависимостей;
5. описывает семантическую навигацию;
6. задаёт destructive acceptance-gates;
7. не меняет runtime;
8. следующая работа может начаться с Release 1 без повторного архитектурного проектирования.

После этой точки архитектуру не меняют по ходу CSS-правок. Новая информация может изменить контракт, но такое изменение оформляется отдельно и осознанно.
