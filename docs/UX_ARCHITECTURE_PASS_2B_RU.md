# UX Architecture Pass 2B — три независимые архитектуры

Дата: 2026-09-28  
Статус: архитектурный проход 2B.  
Назначение: описать три независимых способа организовать существующий функционал калькулятора до сравнительного прохода 2C.

## Общие ограничения, которые считаются заданными

Все варианты обязаны сохранять:
- единое состояние профиля, потребностей, рациона и анализа;
- полный набор нутриентов, включая витамины и минералы;
- HEI-2020;
- Гарвардскую тарелку;
- матрицу качества/структуры;
- коррекцию;
- отчёт и PDF;
- возможность вернуться к потребностям и изменить их;
- отсутствие потери данных при переключении представлений;
- нормальную работу на desktop, tablet и mobile;
- progressive disclosure вместо удаления профессиональной глубины.

В этом проходе варианты не сравниваются и не ранжируются. Каждый описан как самостоятельная полноценная архитектура.

---

# Вариант A — вкладки + постоянный спутник + полный вид

## Основная идея

Приложение организовано как набор постоянных рабочих вкладок:
- Потребности;
- Рацион;
- Анализ;
- Улучшить;
- Отчёт.

Пользователь в любой момент свободно переключается между ними. Это не последовательный мастер.

Рядом с рабочей областью существует компактный постоянный спутник пользователя, который отображает:
- текущий профиль;
- рассчитанные потребности;
- текущее потребление;
- число нутриентов, требующих внимания;
- HEI;
- структуру;
- до трёх главных приоритетов.

Полный длинный вид остаётся вторичным представлением «Все данные».

## Desktop

Композиция:
- постоянная навигация слева или сверху;
- центральная рабочая область;
- справа компактный sticky-спутник, только если ширины достаточно.

На более узком desktop/tablet спутник становится горизонтальной полосой над содержимым.

## Mobile

Основная навигация — нижняя.
Спутник — одна компактная строка, раскрывающаяся по нажатию.

## Анализ

Второй уровень внутри «Анализа»:
- Сводка;
- Нутриенты;
- Качество;
- Структура.

## Сильная сторона архитектуры

Рабочая задача всегда сфокусирована, но базовый контекст не исчезает при переходе между разделами.

## Риски

- постоянная правая панель может отнимать рабочую ширину;
- при плохом ограничении спутник превратится во второй отчёт;
- слишком много вкладок на mobile может перегрузить нижнюю навигацию;
- режим «Все данные» может оказаться редко используемым и создавать лишний выбор.

---

# Вариант B — полотно как основной интерфейс + липкая навигация по разделам

## Основная идея

Вся работа происходит в одной непрерывной вертикальной ленте.

Основные участки:
1. Потребности
2. Рацион
3. Сводка анализа
4. Нутриенты
5. Качество
6. Структура
7. Улучшение
8. Отчёт

Переходы между ними — не смена экранов, а прокрутка к соответствующему якорю.

## Навигация

На desktop:
- sticky-оглавление слева;
- подсветка текущего раздела;
- счётчики/статусы рядом с разделами.

На mobile:
- компактный sticky navigation bar;
- текущий раздел + кнопка «Разделы»;
- при открытии — список якорей.

## Сводка

Не отдельный спутник справа, а sticky-компактная строка в верхней части полотна:
- потребность;
- факт;
- число проблем;
- HEI;
- структура.

При прокрутке она остаётся на экране и помогает не терять контекст.

## Работа с глубокими данными

Нутриенты, HEI, тарелка и рекомендации находятся прямо в ленте, но по умолчанию показываются в сжатом состоянии.

Пример:
- «Витамины: 3 требуют внимания» → раскрыть;
- «Минералы: 2 требуют внимания» → раскрыть;
- «Структура: 31/100» → открыть тарелку;
- «Матрица качества/структуры» → раскрыть большой график.

## Сильная сторона архитектуры

Максимально сохраняется пространственная память и ощущение, что вся информация находится «перед глазами».

## Риски

- при полном раскрытии лента может стать очень длинной;
- сложнее удержать визуальную иерархию;
- глубокая аналитика может замедлять страницу;
- много sticky-элементов может конфликтовать на mobile;
- пользователь может проводить слишком много времени в прокрутке вместо прямого перехода.

# Вариант C — рабочее пространство master-detail

## Основная идея

Приложение устроено не как набор страниц и не как длинное полотно, а как единое рабочее пространство.

Есть три слоя:
- навигация по задачам;
- центральная рабочая область;
- контекстная панель деталей.

Главное отличие: переход к подробностям не всегда меняет страницу.

Например:
- пользователь находится в рационе;
- нажимает «Калий»;
- справа или в bottom sheet открывается детальный разбор калия;
- рацион остаётся видимым;
- после закрытия пользователь возвращается точно туда же.

## Desktop

Композиция:
- левая вертикальная навигация по крупным областям;
- центральная область — текущая задача;
- правая панель — контекст/деталь, которая меняется в зависимости от выбора.

Правая панель может показывать:
- спутник;
- детали выбранного нутриента;
- продукты-вкладчики;
- HEI-компонент;
- рекомендацию;
- структуру.

То есть спутник и инспектор используют одну и ту же область и не конкурируют за место.

## Mobile

Центральная область занимает весь экран.
Контекстная панель становится bottom sheet / drawer.

## Анализ

Главный экран анализа может быть визуальным dashboard:
- энергия и КБЖУ;
- микро-/макронутриентный статус;
- HEI;
- структура;
- несколько приоритетов.

Нажатие на любой элемент открывает подробность в контекстной панели без потери dashboard.

## Сильная сторона архитектуры

Очень хорошо сохраняется связь между общим состоянием и подробностью. Пользователь не «уходит» с текущей задачи.

## Риски

- master-detail сложнее реализовать корректно;
- поведение drawer/inspector может стать непредсказуемым;
- на tablet нужно очень аккуратно определять, когда правая панель ещё уместна;
- если использовать панель слишком часто, интерфейс может напоминать профессиональную IDE и стать слишком сложным для обычного пользователя;
- browser Back/Forward и deep links требуют отдельной дисциплины.

# Что специально НЕ решается в 2B

На этом этапе не выбираются:
- победившая архитектура;
- конкретный шрифт;
- точные размеры спутника;
- окончательная структура mobile-nav;
- окончательные названия разделов;
- точный вид dashboard;
- судьба режима «Лента / Все данные».

Это будет предметом следующих проходов.

# Вход для прохода 2C

Один и тот же пользовательский сценарий должен быть пройден через A, B и C:

1. ввести профиль;
2. рассчитать потребности;
3. перейти к рациону;
4. добавить несколько продуктов;
5. изменить граммовку;
6. вернуться к потребностям и поменять один параметр;
7. открыть микронутриенты;
8. найти конкретный нутриент;
9. посмотреть продукты-вкладчики;
10. понять главные проблемы;
11. открыть HEI;
12. открыть структуру;
13. применить одну рекомендацию;
14. проверить изменение;
15. сформировать отчёт.

В 2C сравниваются:
- число переходов;
- сколько информации приходится помнить;
- количество потерь контекста;
- объём прокрутки;
- количество одновременно конкурирующих элементов;
- устойчивость на mobile/tablet/desktop;
- сложность реализации без дублирования состояния.
