## 1. Чем измерено и как воспроизвести

Добавлен измерительный харнесс, который не трогает приложение:

| Артефакт | Назначение |
|---|---|
| `tests/e2e/ui-audit-capture.spec.js` | проходит 7 маршрутов × 3 вьюпорта; снимает объективные метрики, пошаговые скриншоты и печатный рендер |
| `tools/ui_audit_report.py` | сводит данные в читаемые находки (6 разделов) |

```bash
npx playwright test tests/e2e/ui-audit-capture.spec.js --project=chromium
python tools/ui_audit_report.py
```

Результат складывается в `reports/ui-audit/` (46 скриншотов, JSON-метрики, 21 структурный дамп).

**Ограничения метода, которые важно знать:**

* Оценка построена на измерениях, а не на визуальной экспертизе: я не могу просматривать изображения. Скриншоты сняты именно для вас — их стоит пролистать глазами, они лежат в `reports/ui-audit/shots/` (включая `*-print.png`).
* Контраст считается только для однотонного фона. Текст на градиенте или на изображении помечается как «непроверяемый», а не «плохой».
* Низкий контраст засчитывается как дефект только если элемент подтверждённо отрисован (проверка попадания в точку через `elementFromPoint`). Иначе скрытые копии тех же подписей давали ложные находки — эта ошибка в методике была найдена и устранена в процессе.
* Проверка прав доступа (`permissions`, `storage_policy`) — POSIX-специфична и на Windows неприменима (см. ниже).

## 2. Базовая линия: что проверено до изменений

| Проверка | Результат |
|---|---|
| Браузерный контракт V6: Chromium | **9/9 PASS** (1.2 мин) |
| Браузерный контракт V6: Firefox | **9/9 PASS** |
| Браузерный контракт V6: WebKit | **7/9** — 2 отказа, причина локальная (см. ниже) |
| Аудит-харнесс | **2/2 PASS** |
| Core/safety гейт (26 сьютов) | **24/26 PASS**, 2 отказа — только POSIX-атрибуция |
| Установлено локально для полной проверки | Node 22 + Playwright 1.61 (Chromium, Firefox, WebKit), PHP 8.4 |

Два отказа WebKit (`current needs checkpoint calculates and preserves the profile across steps`
и `mobile profile uses one heading surface…`) воспроизводятся стабильно, в том числе с `--retries=1`,
и **не связаны с приложением**: в WebKit на Windows запрошенный `setViewportSize({width:1024})` не
применяется — измеренный `window.innerWidth` равен 893, поэтому медиазапрос «мобильной» ширины остаётся
истинным и правило `@media(max-width:899px)` законно скрывает контекст навигации. То есть приложение
ведёт себя правильно для фактической ширины 893px, а расходится только предположение теста о размере
окна. Авторитет по WebKit — CI на Linux; локальный WebKit для гейта пока непригоден.

Единственные отказы гейта и их причина:

* `static_integrity → permissions` — `os.stat().st_mode` на Windows синтезируется как `0o666`, поэтому «group/world writable» срабатывает на всех файлах. На Linux проходит.
* `storage_policy` — проверяет `perms == '0700'` у каталога guard; Windows отдаёт `0777`. На Linux проходит.

Ни один из отказов не связан с логикой калькулятора: сьюты расчётов, норм, provenance и HEI-2020 — зелёные.

**Найденный дефект проверяемости (исправлен отдельным коммитом).** `tools/generate_product_provenance.py`
записывал пути (`policy_path`, `source_registry_path`) через `str(Path)`, то есть на Windows с обратными
слэшами. Из-за этого `--check` на Windows всегда сообщал «assets were stale», хотя в репозитории лежит
корректная Linux-версия с `/`. Заменено на `Path.as_posix()`; на Linux поведение не меняется (там эти
выражения тождественны), но локальная проверка стала достоверной. Заодно `runtime_inventory` требовал
создать `api/gemini-secret.php` из примера — так же, как это делает CI.

## 3. Находки

### Критично

**K1. Токен `--muted` используется как цвет текста и в одном из определений равен светло-голубой заливке.**

Токен определён **тремя разными значениями** в одном и том же дереве стилей:

| Где | Значение | Смысл |
|---|---|---|
| `app-bundle-v5.3.117.css:8` (и `app.css:7`, все `runtime-bundle-*.css:11`) | `#DDECF8` | светлая заливка |
| тот же файл, блок темы (`:204`) | `#5b6b7b` | серый — годится и для текста |
| тот же файл, легаси-блок «from v3.6» (`:528`) | `#e7f0ff` | светлая заливка, **перекрывает предыдущие** |

При этом токен массово применяется именно к тексту: `.unit-tag{color:var(--muted)}`,
`p.muted{color:var(--muted)}`, `.kpi .title{color:var(--muted)}`, `.note{color:var(--muted)}`,
`.btn.ghost{color:var(--muted)}`.

Измеренный результат — подтверждённые (отрисованные) прогоны:

| Экран | Контраст | Что именно |
|---|---|---|
| desktop / report | 1.15:1 | «Единый отчёт», «Основные сведения включены всегда», «Дата», «Цель», «Система норм», «Позиций в рационе», «Энергия», «HEI» — всего 12 |
| mobile / report | 1.15:1 | те же подписи (2 подтверждённых, 141 ниже сгиба) |
| desktop / ration | 1.08:1 | «Рацион пока пуст» (15px), «HEI-2020», «Структура» |
| mobile / ration | 1.08:1 | «Рацион пока пуст» (14px) |

Это не косметика: подписи шапки отчёта и текст пустого рациона фактически не видны. Тот же текст в
других местах рисуется нормально (4.76:1) — значит дефект не «везде», а в области, где побеждает
легаси-определение. Лечение — свести токен к одному значению и развести смыслы
(`--muted` для заливки, `--text-muted` для текста). Правка чисто стилевая, логику не затрагивает.

**K2. Пустой рацион показывает аналитическую «начинку», которой не из чего взяться.**

На первом экране пустого рациона (mobile): «Текущий рацион» → «Рацион пока пуст» → «Добавьте первый
продукт через поиск ниже.» → и сразу **шесть KPI-подписей** (Калории, Белки, Жиры, Углеводы, HEI-2020,
Структура) плюс кнопка «Перейти к анализу» и предупреждение «Потребности не рассчитаны». Всего 34
отрисованных прогона на первом экране, из них большая часть — про то, чего ещё нет.

Это ровно та проблема, которую закрывает незамёрженный пасс 4 (`ux/interface-pass4-empty-state`):
скрывать аналитику при пустом рационе и возвращать её после первого продукта. Находка подтверждает,
что это верное направление, а не вкусовщина.

### Важно

**V3. Типографика без шкалы.** Рендерится 27–29 различных размеров на каждый вьюпорт, из них дробные
значения из `rem` (12.16, 12.48, 12.8, 14.56px). Ниже 12px:

| Вьюпорт | Прогонов | Размеров | < 12px |
|---|---|---|---|
| mobile | 781 | 27 | **152 (19.5%)** |
| tablet | 768 | 29 | **140 (18.2%)** |
| desktop | 865 | 29 | 105 (12.1%) |

Самый частый мелкий размер на mobile — **9.5px, 76 вхождений**. Пятая часть текста на телефоне ниже
разумного минимума, и это главный источник ощущения «мелко и неудобно».

**V4. Экран отчёта — это документ, а не экран.** mobile: **10.98 экранов** прокрутки при всего 12
интерактивных элементах и 6 кнопках; desktop — 5.57 экрана; 10 заголовков. Для телефона это самый
дорогой маршрут. Печатный рендер снят (`*-print.png`) и будет разбираться отдельным этапом.

**V5. Тап-таргеты на телефоне.** В «Рационе» 12 целей ниже 40px: переключатели «Таблица / Подробнее /
Тарелка» — 280×32, чипы порций «50/100/150/200 г» — 160×36, «Найти первый продукт» — 174×38,
«Очистить рацион» — 322×39, «Перейти к анализу» — 267×38. Высота 32–39px при ширине 160–322px —
это «широкие, но низкие» кнопки: по ним легко промахнуться именно из-за малой высоты.

**V6. Служебная информация в продукте.** В шапке каждого экрана видна строка версии 9px, причём
**разная на разных маршрутах** — на «Рационе» и «Профиле» `v6.0.0-beta6-hotfix3`, на «Анализе»
`v6.0.0-beta6-hotfix4`. Либо это два разных штампа на одном интерфейсе, либо устаревшая копия.

**V7. Плотность конкурирующих элементов.** После исключения скрытых: desktop «Рацион» — 49
интерактивных, mobile «Рацион» — 35, mobile «Профиль» — 32, desktop «Анализ HEI» — 40.

## 4. Что этим этапом НЕ проверено

* **Визуальная экспертиза.** Композиция, «воздух», выравнивания, ритм — по измерениям не выводятся.
  Нужен ваш взгляд на 46 скриншотов; я работаю по числам и структуре DOM.
* **Клинические сценарии и точность формул.** Прогонялись только гейты (формульный реестр 29 формул /
  113 golden-кейсов, нормрегистр, HEI-2020). Содержательная клиническая оценка — отдельный этап.
* **Структура рациона / «тарелка» и плотность продуктов.** Не разбиралась; это отдельный расчётный
  сюжет, и его нельзя трогать без предварительного разбора.
* **Неретро-темы и печатная вёрстка.** Рендеры сняты, но не разобраны.
* **Контраст на градиентах** — помечен как неизмеримый данным методом (честно, а не «в порядке»).

## 5. Предлагаемый порядок работы

Каждый этап: минимальное изменение → прогон браузерного контракта и core-гейта → содержательный
коммит в `deepseek-ui`.

| Этап | Что | Риск для логики |
|---|---|---|
| **E1** | Токены и контраст: развести `--muted`, убрать нечитаемые значения, поднять акцентный зелёный до AA. Отдельно: служебный штамп версии из шапки | нет (только CSS) |
| **E2** | Типографическая шкала: свести 27–29 размеров к ~8–9, поднять минимум до 12px (9.5px → 12px), убрать дробные `rem` | нет (CSS) |
| **E3** | Тап-таргеты ≥ 40px по высоте в мобильном рационе и профиле | нет (CSS) |
| **E4** | Пустые состояния и иерархия: разобрать пасс 4 и продолжить на `correction`, `report`, профиль без норм | нет (композиция) |
| **E5** | Отчёт и печать: сжать 11 экранов, порядок блоков, печатная вёрстка | низкий |
| **E6** | Клинические сценарии и «тарелка»/плотность | **требует отдельного разбора и вашей приёмки** |

Порядок продиктован обратимостью: E1–E3 — чистая стилевая правка с мгновенной проверкой, E4–E5 —
композиция, E6 — единственный этап, который может изменить числа.

### Про незамёрженные ветки

`ux/interface-pass4-empty-state` (6 коммитов), `ux/interface-audit-post3`, `ux/interface-audit-2026-09-22`
и `fix/production-ui-recovery` (11 коммитов) существуют только на remote и в `main` не влиты. Они
правят те же `index.html` и `tests/e2e/v6-canonical-ci.spec.js`, что и дальнейшая работа, поэтому

Решение по ним за вами; в `main` я ничего не вливаю.

## 6. Как запустить интерфейс и посмотреть своими глазами

Приложение статическое, поэтому для реального прогона не нужен ни сборщик, ни PHP — достаточно
отдать корень репозитория по HTTP. Три способа, от простого к «как в проде»:

| Способ | Команда | Что работает |
|---|---|---|
| Статический сервер проекта | `npm run serve` → http://127.0.0.1:4173/index.html | весь калькулятор; AI-роут замокан |
| С телефона по локальной сети | `npm run serve:lan` → `http://<IP-компьютера>:4173/index.html` | то же, но на реальном устройстве |
| Настоящий PHP-бэкенд | `npm run serve:php` → http://127.0.0.1:8080/index.html | всё то же плюс живой `api/gemini.php` |

Открыть в своём браузере:

```bash
npm run serve
start http://127.0.0.1:4173/index.html      # Windows
```

Отдельно есть прогон «как пользователь» в настоящем браузере, без перехвата сети:

```bash
npm run smoke:real                                    # headless, скриншоты и PDF в reports/real-run
node tools/real_run_smoke.cjs --headed --slowmo=250   # смотреть, как всё происходит
node tools/real_run_smoke.cjs --port=8080             # против живого PHP-бэкенда
```

**Результат прогона на 22.09.2026** (10 шагов, ноль ошибок консоли, ноль отказов запросов):

| Шаг | Результат |
|---|---|

| поиск | «банан» → 5 вариантов |
| рацион | продукт добавлен, **304 ккал · 4% от ориентира** |
| обзор анализа | 2149px на телефоне |
| дашборд HEI-2020 | 2214px на телефоне |
| отчёт | **9780px** на телефоне (подтверждает V4 уже на живом сервере) |
| печать | PDF **194 КБ** |

Скриншоты и PDF: `reports/real-run/`.

### Два побочных наблюдения из реального прогона

* **`hosting-check.html` устарел.** Он требует, чтобы `api/gemini.php` отдавал ровно
  `version === "v5.3.210-rc2"`, тогда как фактический бэкенд отвечает `v5.3.210-rc2-hf28`. На живом
  хостинге самопроверка покажет «ERR API», хотя API исправен. Это ложная тревога в инструменте, а не
  дефект продукта.
* **`configured`/`ai_available` не отличают плейсхолдер от настоящего ключа.**
  `configured` вычисляется как `count($keys) > 0`, а `api/gemini-secret.example.php` возвращает
  `['primary' => 'REPLACE_WITH_PRIMARY_GEMINI_KEY', ...]`. Поэтому локально интерфейс сообщает, что AI
  доступно, хотя реальный вызов провайдера с таким «ключом» не пройдёт.
